# 旅行可达锚点与终态收敛设计

## 背景

真实洛阳计划证明，高德手机端“能导航”不等于公交 API 能直接以景区中心坐标返回线路。`栾川汽车站 -> 老君山风景名胜区` 使用山体中心 POI 时返回 `transits=[]`，旧路线任务随后把该段保留为公共交通规划估算，最终器按真实证据门槛拒绝保存。与此同时，父 Turn 已经结束并持久化 finalizer 错误后，旅行页仍可能保留“正在生成最终计划”的本地运行态，直到刷新或重启才恢复。

## 目标

- 远郊景点公交首查为空时，改查同一景点的游客中心、入口或售票处等可达锚点。
- 可达锚点仍无公交时，使用高德驾车距离和时长形成透明的出租车/网约车兜底，不伪造公交线路。
- 住宿与路线并行后，只允许路线使用已经确定的具体住宿锚点；缺失的酒店相关路线进入有界补路，不再接受另选酒店。
- WebSocket Turn 终止后立即以服务端 Generation 状态收敛 UI，不等待刷新。
- 路线修复时只显示路线 Lane，已完成住宿 Lane 不回退到运行中。

## 范围边界

- 不接入叫车、支付或下单。
- 不把网页攻略描述冒充高德公交结果。
- 不放松已有公交证据门槛：只要展示公交/地铁，就必须有线路、上下车站、距离和时长。
- 高德确实无公交时允许展示高德驾车兜底，并明确它不是已核验公交。

## 模块设计

### 路线 Child

`travel-final-route` 增加高德驾车能力，并采用三层策略：

1. 对所选路线的真实起终点查询公交。
2. 景区中心返回空数组时，只对同一景区查询一次游客中心/主入口/售票处候选，选择同区且名称相关的可达 POI 后再查公交。
3. 仍无公交时查询一次高德驾车，输出距离、时长及“出租车/网约车兜底”；不得生成虚构线路或站点。

公交与驾车响应都在 Child ToolProvider 边界压缩，避免原始路径挤占模型上下文。

### 最终器

最终器继续拒绝大于等于 2 公里的公交或 `planning_estimate` 段缺少公交腿。高德驾车兜底必须使用非公交 mode 和高德来源，因此不会被误判成“假公交”；其证据仍由 Evidence schema 校验。

### 前端终态

收到当前旅行 Session 的 `done`、`stopped` 或 `error` 后，立即请求 `/api/travel/generation`。服务端返回的 `completed/failed/awaiting_candidate` 覆盖本地推断。只有状态接口暂时失败时才保留 WebSocket 兜底文案。

恢复最终化进度时根据持久化 Progress 判断 Lane：住宿已完成而交通未完成时，只创建/恢复交通 Lane，并显示“正在补齐缺失的公共交通路线”。

## 数据流

```text
候选已选
  -> stay Child 与 route Child 并行
  -> 固定实际酒店 POI
  -> 公交到景区中心
       -> 有线路：保留线路/站点
       -> 空结果：游客中心/入口再查
            -> 仍为空：高德驾车兜底
  -> finalizer
  -> WS 终态
  -> Generation API 覆盖前端本地状态
```

## 测试方案

- 单测公交空结果后驾车响应压缩与 Profile 工具边界。
- 单测路线修复 Prompt 明确可达锚点和驾车兜底。
- 前端单测 `done` 后立即读取服务端终态。
- 前端单测住宿 Lane 已完成时不恢复为 running。
- 真实洛阳计划验证老君山段、两晚酒店、按天地图、终态自动展示与刷新恢复。

## 验收标准

- 不再以老君山山体中心公交空结果无限阻塞整份计划。
- 公交存在时展示线路号、上下车站；不存在时明确展示高德驾车兜底。
- 页面无需刷新即可从运行态进入失败可续跑或完整计划。
- 路线修复阶段不再显示住宿仍在查询。
