# 旅行证据同 URL 去重修复设计

## 背景

旅行终稿会把地图 POI、酒店地点和公共交通路线保存为独立证据。高德结果可能统一使用 `https://ditu.amap.com/` 等入口 URL；现有证据去重除内容哈希外，还按“来源提供方 + 规范化 URL”合并证据，导致同一入口 URL 下语义不同的酒店证据被重映射为更早的景点或路线证据。住宿身份校验随后无法在被重映射的证据中找到酒店名称或地址，持续返回 `TRAVEL_PLAN_SCHEMA_INVALID`。

## 目标

- 同一提供方、同一 URL 但内容不同的证据必须分别保留。
- 内容完全相同、仅跟踪参数不同的重复证据仍应合并，并正确重映射引用。
- 住宿身份证据不得因地图入口 URL 相同而错误指向普通 POI。

## 范围边界

- 只调整 `TravelPlanV1` 内的证据去重判定，不改变 EvidenceItemV1 字段、来源真实性校验或住宿匹配规则。
- 不放宽未知证据引用、酒店名称/地址匹配和外部价格证据要求。
- 不修改 AgentLoop、旅行自动续跑或外部数据源调用策略。

## 模块设计

`EvidenceItemV1.content_hash` 已覆盖 provider、标题、规范化 URL、摘要和事实，并在 URL 规范化时移除 UTM 跟踪参数。证据去重改为只按该完整内容哈希合并，不再把 provider 与 URL 相同视为内容相同。

引用别名表继续保留：只有完整内容哈希重复时，后出现的 `evidence_id` 才映射到先出现的证据。语义不同但共享入口 URL 的证据分别进入 `evidence_by_id`，住宿、活动和路线引用均保持原 ID。

## 数据流

1. 解析每条原始 EvidenceItemV1，并计算规范化内容哈希。
2. 按内容哈希查找完全重复证据。
3. 重复时记录 ID 别名；不重复时保留为独立证据。
4. 各业务字段通过别名解析引用并执行既有语义校验。

## 变更文件

- `agent/applications/travel/schemas.py`：移除 provider + URL 的宽松去重分支。
- `tests/unit_test/travel/test_schemas.py`：增加同一高德入口 URL 下 POI 与酒店证据并存的回归测试。
- `tests/unit_test/travel/test_case.md`：补充本缺陷的测试覆盖说明。

## 测试方案

- 保留既有“内容相同但带不同 UTM 参数”的去重测试，验证精确重复仍合并。
- 构造 provider 和 URL 相同但标题、摘要、事实不同的地图 POI 与酒店证据，验证两者均保留且住宿引用仍指向酒店证据。
- 运行旅行 schema 定向测试、旅行单元测试主题和 Ruff。

## 验收标准

- 共享地图入口 URL 的酒店证据不再被重映射为景点或路线证据。
- 既有精确重复证据去重行为不回退。
- 旅行相关测试与 Ruff 通过，diff 不包含当前任务范围外的改动。
