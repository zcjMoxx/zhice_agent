# 县域交通与候选阶段恢复设计

## 背景

旅行规划的候选阶段同时使用持久化的三路 Child 完成记录和进程内来源账本。县域目的地没有可用铁路站码时，交通 Child 会正常完成，但账本仍要求去返程各执行一次 12306 票务查询；运行时随后禁止再次委派，而工具守卫又只开放委派入口，形成无法进入 optimizer 的循环。

同一真实计划还暴露出两个外部来源边界问题：携程目的地输入使用“省市前缀 + 县”时只匹配完整字符串，无法选择页面实际返回的县级目的地；目标日期处于预报窗口时必须统一使用实时预报，不能被模型降级成历史同期数据。

## 目标

- 三路候选研究的完成事实成为候选阶段唯一共享门槛，提示词、工具开放和续跑判定使用同一状态。
- 铁路查询保持严格：两端都有已验证站码时，仍要求去返程各查询一次；一端无站时将铁路标记为不适用，并允许使用大巴、自驾、包车等透明降级方案。
- 携程对常见省、市前缀进行有界规范化，仍只点击页面可见且与目标一致的候选。
- 目标日期在实时预报窗口内时，只允许 forecast；窗口外才允许历史气候参考。
- 无效续跑尽早结束为可诊断状态，不再重复消耗候选阶段轮次。
- `/travel` 无显式计划参数时保持新建草稿，不把旧失败任务的对话混入新计划。
- 唯一候选自动选中事件可被运行时协议正常投递；小红书详情读取不再误显示为搜索空结果。
- 站码适用性证据不再被误当成真实车次证据；高德米制路线距离进入计划前统一换算为公里。
- 实时天气卡兼容计划中的 `overview`、温度范围和最高降水概率字段，不再只显示占位符。

## 范围边界

- 不为忠县或任何单个目的地增加特例。
- 不伪造汽车班次、票价或铁路站码；没有真实来源时明确标为规划估算。
- 不扩大铁路、酒店或天气的调用预算。
- 不改变通用 AgentLoop；全部逻辑保留在旅行应用边界、Prompt、Skill 和适配器内。

## 模块设计

### 候选研究状态

`TravelSourceLedger` 保存已完成的候选研究 Profile。只有固定三路 Profile 全部以 `completed/OK` fan-in 后，`candidate_research_complete` 才成立。`candidate_missing_attempts` 在该状态下为空，`TravelResearchRequiredToolProvider` 随即隐藏 `delegate_tasks` 并开放 `load_skills`、`run_skill`。

当前 Turn 通过委派回调写入完成 Profile；进程重启后从父 Session 的持久化委派结果恢复同一事实。续跑提示、强制委派和工具过滤均读取这一状态。

### 铁路适用性与公路降级

来源账本分别记录站码查询和票务查询。研究批次未完成时，两端有站码仍需两次 dated ticket attempt；研究批次已经完成但不足两个站码时，铁路只表示不适用或未知，不再阻塞候选求解。

规划 Prompt 和 travel-planner Skill 要求：无铁路站时优先形成大巴、自驾或包车方案；真实汽车站、班次或攻略价格可作为来源，没有时只能给范围估算并写入 unknowns。只有用户明确偏好铁路时，才考虑最近铁路站加接驳。

### 携程目的地规范化

浏览器适配器依次尝试原始目的地和至多一个去除中国省级行政前缀的候选，例如“重庆忠县”规范为“忠县”。每次仍要求页面候选可见，且输入框最终值与当前候选相互包含；不做无限别名重试。

### 天气窗口

服务端按北京时间生成日期窗口事实。窗口内的历史天气调用由工具守卫直接拒绝且不消耗有效天气尝试；交通天气 Child 和最终天气修复都必须使用 `get_forecast`。窗口外才把上一年同期数据标为历史气候参考。

前端天气卡同时消费 `summary`、`condition` 和当前计划契约使用的 `overview`，并展示最低/最高温和最高降水概率。来源与 freshness 仍独立展示，实时预报和历史参考不混用。

### 交通证据与单位契约

12306 城市/站码查询只用于判断铁路是否适用。只有包含车次、出到达、席别、余票或票价事实的证据才会触发真实铁路方案的完整字段校验；县域无站时，公路方案可以引用站码查询来解释降级原因，但不会被要求伪造车次。

高德路线原始距离为米，`TravelPlanV1.route_segments[].distance` 对外为公里。最终化入口只在来源明确为高德且数值超过计划公里上限时执行米到公里换算，`walking_distance` 继续保持米制。

### 新建页面恢复边界

只有正在运行、等待候选、已选择候选待继续，或 URL 显式包含 `plan`/`session` 时恢复对应工作区。普通 `/travel` 不再自动打开列表中的第一条未完成任务；历史失败任务继续保留在左侧列表，由用户明确点击后查看或继续。无持久化 Session 时不向生成状态 API 发送空 Session ID，旧版本遗留的普通失败 Session 也会清除并回到空白新建态。

## 数据流

1. 父 Agent 一次委派固定三路候选研究。
2. Child 调用受限外部来源；交通 Child 先查两端站码，再按适用性查询票务与天气。
3. fan-in 回调记录三个完成 Profile；重启时由 Session 历史恢复。
4. 候选工具守卫读取同一完成状态，开放 Skill 与 optimizer。
5. optimizer 在铁路不适用时使用透明的公路交通方案，生成候选卡。
6. 用户选择后进入既有住宿与本地路线最终化流程。

## 测试方案

- 单测覆盖三路完成后即使铁路票次数为零也开放 optimizer。
- 单测覆盖三路未完成且两端有站码时仍强制两次票务查询。
- 单测覆盖 Session 重启后从持久化 fan-in 恢复候选完成状态。
- 单测覆盖“重庆忠县”依次尝试完整名称和“忠县”。
- 单测覆盖预报窗口内拒绝历史天气、允许实时 forecast。
- 单测覆盖站码查询不触发铁路车次字段要求，以及高德米制路线距离的有界换算。
- 前端单测覆盖实时天气概况、温度与降水概率展示。
- Fake E2E 覆盖县域无站码仍生成候选并完成计划。
- 最后运行 Ruff、全量 Pytest、本地真实服务与浏览器链路，并在部署后复测线上 Owner 计划。

## 验收标准

- 重庆南岸到忠县的计划不再卡在候选阶段，也不重复委派五轮。
- 无铁路站时能出现候选卡，交通明确展示大巴/自驾/包车来源或估算属性。
- 携程能以县级候选继续查询，失败时保留明确错误而不伪造价格。
- 预报窗口内的最终计划不再展示历史同期天气。
- 最终计划可保存完成，页面进度稳定到完成态；服务部署后健康且无新增重启。
