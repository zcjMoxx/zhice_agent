# 工作流当前画布发布与运行一致性设计

## 背景

当前编辑器把“保存草稿”“发布”“立即运行”作为三个互不关联的按钮。发布接口只读取数据库中的旧草稿，立即运行只读取旧的已发布快照；用户在画布上新增节点后直接发布或运行时，界面仍显示“已发布”和“执行成功”，但实际可能只执行旧版本中的部分节点。

实测问题工作流的当前草稿包含“开始、获取信息、发送结果”三个节点，已发布版本 1 只有“开始”，两次成功运行也都只有开始节点，邮件投递记录为零。

## 目标

- 点击发布时，自动保存并发布当前屏幕上的完整画布。
- 点击立即运行时，自动保存、发布并运行当前屏幕上的最新版本。
- 已发布版本保持不可变；首次修改已发布版本时，后端自动创建下一版本。
- 页面明确区分“未保存修改”“待发布”和“已发布”。
- 修复已经被旧逻辑写入同版本草稿的现有数据，无需用户重建工作流。

## 范围边界

- 保持 Workflow Runtime 独立于 AgentLoop 和聊天 Session。
- 不允许直接执行未校验草稿；运行前仍经过发布校验、连接所有权、权限和动作授权检查。
- 不改变定时调度的已发布版本真值语义。
- 不改变运行历史和投递事实；没有执行发送节点时不得产生投递记录。

## 模块设计

### 后端版本规范化

`WorkflowStore.save_draft` 读取当前 `active_version`。当客户端仍提交活动版本号，但内容已不同于该不可变发布快照时，服务端自动把草稿提升为 `active_version + 1`。后续保存同一未发布草稿不重复递增。

Store 提供当前活动版本、最新草稿版本和是否存在未发布修改的元数据。REST 列表、详情、保存和发布响应统一返回这些字段。

### 前端操作语义

- 保存草稿：保存当前画布，更新本地保存基线。
- 发布：保存当前画布；如果存在未发布版本，再发布该版本。
- 立即运行：保存当前画布；如果存在未发布版本，先发布；随后运行最新活动版本。
- 返回工作流首页：继续自动保存当前画布。

### 状态反馈

编辑器维护当前画布与最近保存基线的稳定指纹：

- 当前画布不同于保存基线：显示“未保存修改”。
- 已保存草稿版本高于活动版本：显示“待发布”。
- 两者均否：显示活动、暂停或草稿状态。

当存在修改时，页面提示“发布和立即运行都会自动使用当前画布”，避免用户记忆按钮顺序。

## 数据流

```text
用户编辑当前画布
  -> 点击发布：保存（必要时 v1 -> v2）-> 校验 -> 发布 v2
  -> 点击立即运行：保存 -> 校验并发布最新版本 -> 执行最新活动版本
  -> 运行历史记录完整节点；发送节点执行后才记录邮件投递
```

## 变更文件

- `agent/workflows/store.py`：版本提升、草稿持久化时间和状态元数据。
- `agent/app/api/workflow_routes.py`：工作流响应统一携带版本状态。
- `web/frontend/src/api/types.ts`：活动版本和未发布状态类型。
- `web/frontend/src/stores/workflows.ts`：保存后发布、保存发布后运行。
- `web/frontend/src/pages/WorkflowPage.vue`：画布指纹、状态提示和新操作语义。
- `web/frontend/src/styles/workflow.css`：未保存与待发布状态样式。
- 后端 Store 测试和前端 Store/页面测试覆盖完整链路。

## 测试方案

- 已发布 v1 被修改后保存，自动生成 v2，活动版本仍为 v1且标记待发布。
- 再次保存 v2 不重复递增，发布后活动版本变为 v2且待发布标记消失。
- 发布操作调用顺序固定为保存后发布。
- 立即运行调用顺序固定为保存、必要时发布、运行和刷新运行详情。
- 当前画布修改后展示“未保存修改”；保存后未发布展示“待发布”。
- 运行 Ruff、相关 Pytest、前端测试、ESLint、类型检查、生产构建和真实浏览器验收。

## 验收标准

- 用户无需记忆“保存 → 发布 → 运行”的顺序。
- 点击立即运行后，运行记录中的节点与当前画布一致。
- 旧活动版本不会被原地覆盖。
- 不再出现只有开始节点却误导用户认为当前三节点画布已执行的情况。
