# 旅行来源查询与需求选择闭环修复设计

## 背景

真实河南旅行规划暴露出四个同源问题：小红书已经返回公开笔记，但长嵌套 JSON 在进入旅行来源账本前被截断，界面误判为空；高德地点与路线批量调用超过账号 QPS，且项目内地点、详情与路线预算不适合多城市长行程；缺少显式行政区字段的正确高德结果被地址文本误判为异地；旅行基调卡只修改前端本地表单，未立即持久化，导致选择后仍显示旧问答、刷新才折叠。

最终计划还直接展示 `amap_transit`、`model_estimate`、`ctrip-account-observation` 等内部枚举，不符合用户界面中文口径。

## 目标

1. 小红书真实返回必须形成可解析、可展示、可进入 evidence 的有界摘要。
2. 攻略检索遵循确定性两层规则：首次为“目的地旅游攻略”；仅在真实空结果时，允许一次“单景点攻略”重试。
3. 高德并发调用在应用边界统一节流；QPS 超限只进行一次有界重试。
4. 多城市行程保留有界但足够的地点、详情和路线调用额度。
5. 只有高德明确返回异地行政区时才拒绝；缺省行政区但启用 citylimit 的结果不得误杀。
6. 旅行基调卡只在其余必填项齐全后出现；选择后立即持久化、折叠为一条选择记录并开始规划。
7. 计划页面不直接展示内部英文来源与时效枚举。
8. Tavily 查询保持单一城市攻略意图，并从展示摘要中剔除英文平台模板噪声。
9. 天气坐标优先复用高德城市定位，不让 Open-Meteo 同名村镇进入规划过程。
10. 高德路线响应中的米统一换算为最终计划使用的公里，避免 1245 米显示成 1245 公里。
11. 预报窗口内禁止用历史同期天气冒充实时预报；Tavily 页面显示守卫归一后真正执行的关键词。
12. 高德长公交响应被截成中段片段时，不展示无法确认属于整条路线的距离和耗时。
13. 最终住宿/路线 Child 成功后，同一 Turn 立即切换到 finalizer；跨 Turn 或进程重启从父 Session fan-in 恢复完成状态。

## 范围边界

- 不改变通用 AgentLoop。
- 不增加小红书写操作，也不读取或展示 Cookie、token。
- 不取消来源调用上限；只按多城市长行程的真实规模拆分并调整预算。
- 不把高德手机 App 的产品能力等同于 Web API；本次只处理当前 AMap MCP 已开放接口的调用节奏、返回解析和降级语义。
- 不让旅行基调选择绕过服务端 `confirm-planning` 完整性校验。

## 模块设计

### 小红书

- `TravelGuardedTool` 在调用前把组合词规范为单一检索意图。
- 首次组合词取第一个目的地实体并生成“目的地旅游攻略”；模型的唯一重试必须传一个景点，服务端统一为“景点攻略”。
- 首搜有笔记时不再改关键词；若搜索卡只有标题、缺少可引用摘要，可对筛选后的一篇笔记做一次只读详情补全。详情调用使用独立一次预算，不计入搜索重试，也不能扩成多篇抓取。
- `source_ledger` 在通用 MCP 结果截断前抽取最多六条笔记的标题、作者、公开链接引用和短摘要，去除 `xsecToken`、头像、封面和互动大对象。
- 结果存在公开笔记时标记 social 成功，前端显示真实返回数量，不再提示空结果。

### 高德

- 所有旅行态 AMap Tool 共享进程级节流门，默认最小间隔 0.35 秒。
- 精确识别 `CUQPS_HAS_EXCEEDED_THE_LIMIT`，在同一受控调用内等待后重试一次；不消耗额外模型迭代与来源预算。
- 城市 geocode 的 `return` 包装直接投影为行政区与坐标，不再把成功响应显示成“没有地点候选”。超长路线被 MCP 插入 `[truncated middle]` 时，进度卡只读取保留头部的 route 总距离与首条公交信息，不能递归误取内部步行 step。
- 来源结果元数据额外保存严格白名单内的真实生效查询参数，历史恢复优先采用该值，避免模型原始组合词与运行时归一化关键词在刷新前后不一致；Cookie、token、key 和任意未列入白名单的字段一律不持久化。
- `walking_distance` 继续统一为米，但不再把 2 公里当作结构合法性的硬上限：高德真实景区公交可能返回 2 公里以上接驳步行。最终协议允许 0–50000 米并原值展示，路线舒适度仍由候选求解器和旅行基调判断，而不是篡改真实数据。
- 地点文本搜索、地点详情、路线分别计数；候选地点允许“初查 + 每个缺失项最多一次窄化”，路线额度覆盖多日计划的全部关键接驳。
- 城市过滤优先读取 province/city/district 等显式行政字段；只有这些字段明确指向异地才拒绝。仅有普通地址时依赖已注入的 `citylimit=true`，不误报异地。

### 需求选择闭环

- 旅行基调卡的前置条件是出发地、目的地、日期、人数均已齐全且日期有效。
- 接待模型提交的核心字段还必须能在当前用户 Turn 中找到明确依据：目的地需被用户提及，出发地需有“从 X 出发 / 我在 X”等语义，日期需有日期锚点，人数需有明确人数表达。模型自行填今天、1 人、同城出发等默认值会在 Tool 边界被丢弃。
- JSON Schema 示例占位词（如 `string`、`unknown`）不会进入偏好数组、约束或用户侧记录。
- 助手只提示“请选择旅行基调”，不再用文本重复枚举三项。
- 卡片上明确提示可选偏好入口；用户需要补充时先打开表单。
- 点击基调后立即把“已选择旅行基调：X”写入需求记录，保存草稿并调用既有确认接口；卡片同步消失，不再要求二次点击确认。

### 展示本地化

- 前端维护来源、路线来源和 freshness 的中文映射。
- 未知新 provider 保留安全原值，已知内部枚举一律不直接暴露。
- Tavily 展示摘要只保留可读的中文旅行事实，点赞、订阅、登录等英文平台模板不进入进度卡。
- Tavily 压缩结果回填守卫归一后的有效 `query`，进度卡以该值覆盖模型原始组合词，保证页面展示与真实调用一致。
- Open-Meteo 地名候选属于内部坐标核对过程，不直接展示可能尚未通过行政区域校验的同名地点。

### 天气地点消歧

- `travel-transport-weather` 优先调用高德城市地理编码，并把已核验经纬度直接用于 Open-Meteo 天气查询。
- 只有高德城市定位不可用时才回退 Open-Meteo 地名搜索；省份或国家冲突的同名地点不得用于 forecast。
- 行程处于北京时间未来 16 日预报窗口内时，历史天气 Tool 在调用远端前返回 `TRAVEL_LIVE_FORECAST_REQUIRED`，且不计为天气已尝试；模型必须改用核验坐标调用实时预报。
- 公交进度只有在完整 `route` 外壳仍可解析时才展示路线总距离与总耗时；截断片段只展示可核验的线路号、上下车站，避免把 275 米步行段误报成酒店到白马寺的总距离。

### 多住宿区价格闭环

- 候选跨越多个过夜区域时，最终住宿 Child 按每个不同城市或区域及其真实入住区间分别查询一次，而不是只查目的地市区。
- 住宿来源不再以“任一成功即停止”拦截同一候选的第二住宿区；完全重复参数仍由指纹守卫拒绝，整个 Session 仍受三次住宿预算限制。
- 每个最终住宿都必须同时具备严格同名的高德酒店身份和对应日期的携程观察价；不能拿洛阳市区价格覆盖栾川住宿，也不能把未核验项继续写成实时价。

### 最终化完成状态

- 最终化的“来源 Tool 已调用”和“固定 Child Lane 已成功完成”是两个不同事实。住宿 Child 可复用候选阶段已核验的携程观察，只补高德身份；此时不能因为没有第二次酒店 ToolResult 就把住宿 Lane 永久判为缺失。
- `delegate_tasks` 返回后按 task id 关联 Profile，只有子任务同时满足 `status=completed` 与 `code=OK` 才标记对应 Lane；失败、超时、取消和部分未完成项均不标记。
- Lane 标记在 `delegate_tasks` 同一次执行返回时写入来源账本，使外层 Provider 下一次生成工具定义时立即只暴露 `finalize_travel_plan`，不等待新 Turn 或刷新。
- 进程重启后从父 Session 持久化的 assistant 调用参数与对应 tool fan-in 结果恢复完成 Lane；Child 内部来源消息只回放当前仍缺失的类别，避免重复增加调用计数。

## 数据流

```text
旅行草稿齐全（仅缺基调）
  -> 显示三张基调卡与可选偏好提醒
  -> 用户选择
  -> 保存选择记录与完整草稿
  -> confirm-planning
  -> 并行旅行研究
       -> 小红书关键词规范化 -> 有界笔记摘要
       -> 高德共享节流门 -> 一次 QPS 重试 -> 城市严格校验
  -> 候选/最终计划
       -> 最终住宿/路线 Child completed+OK
       -> 同轮开放 finalizer
  -> 中文来源标签展示
```

## 测试方案

1. 小红书 RedNote camelCase 长结果在截断阈值以上仍抽取最多六条并判定成功。
2. 组合关键词被规范为“河南旅游攻略”，单景点关键词保持“老君山攻略”。
3. 并发高德调用通过共享节流门串行进入；QPS 错误只重试一次。
4. 缺 cityname、仅有景区地址的 citylimit 结果保留；明确异地行政字段仍拒绝。
5. 地点搜索、详情和路线预算分别生效，不因详情查询耗尽地点搜索额度。
6. 基调卡只在其余必填条件齐全时出现，选择一次即提交并折叠，刷新后记录一致。
7. 页面显示“高德公交路线 / 规划估算 / 携程账号实查”等中文标签。
8. 真实浏览器走完整需求收集流程，验证无需刷新、无需二次确认。
9. 跨洛阳市区与栾川过夜的候选可执行两次不同日期/区域的酒店查询，且两张住宿卡分别保留身份与观察价。
10. Tavily 原始组合词经守卫归一后，进度卡只显示有效查询；未来 16 日内历史天气调用被拒绝且不消耗天气尝试。
11. 最终住宿只复用候选酒店观察、没有再次调用酒店 Tool 时，completed+OK 仍使住宿 Lane 完成；路线 Lane 同理。
12. 一项成功一项失败的 partial fan-in 只标记成功项；两项成功后同一 Turn 工具定义由 `delegate_tasks` 切换为 `finalize_travel_plan`。
13. 重启后从父 Session 恢复已成功 Lane，不重复委派；缺失或非 OK 项保持可补查。
14. 真实输入“我想去洛阳玩”只记录目的地；即使模型提交洛阳出发、当天往返、1 人、100 元和 `string` 占位，服务端仍返回缺少出发地、日期、人数和基调，页面不得提前显示基调卡。

## 验收标准

- 计划页不得直接展示 `TravelPlanV1`、`quick`、`deep`、`AMap`、`Ctrip`、`amap_transit`、`model_estimate` 等内部枚举；统一显示中文业务标签。

- 已返回的小红书笔记不再显示为“未查到”。
- 河南长行程不会因同批高德请求触发连续 QPS 失败；若外部仍限流，界面明确说明而非笼统“未取得结果”。
- 白马寺、洛邑古城这类缺 cityname 的正确结果不再被误判异地。
- 基调选项不提前出现；点击后 1 次完成选择、折叠和启动规划。
- 最终用户页面不出现已知内部英文来源枚举。
- 最终住宿与路线 Child 成功后，无需刷新即可进入最终计划保存，且不会再次出现 `TRAVEL_SUBAGENT_BATCH_INVALID` 重复委派循环。
