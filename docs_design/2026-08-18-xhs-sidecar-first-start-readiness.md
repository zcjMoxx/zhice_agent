# 小红书 Sidecar 首次启动就绪窗口

## 背景

Part 19 云端发布实测中，小红书 sidecar 首次启动需要下载并解压约 140–190 MB 的固定浏览器。本机同镜像实测耗时约 197 秒，而部署和固定拓扑重启原先只等待 180 秒，导致端口即将就绪时被误判失败并回滚。Paramiko 远端发布总等待上限原为 300 秒，也不足以覆盖较慢服务器网络下的首次下载。

## 目标

- 首次无缓存部署在慢速网络下仍可完成。
- 后续部署继续复用 `zhice-xhs-cache`，不重复下载。
- 等待必须有明确上限，失败时提供足够但有界的日志。
- 保留现有不可变 Digest、旧容器回滚和公网健康验收边界。

## 范围边界

本次只调整云端部署、固定拓扑重启、远端 SSH 等待和相应文档测试。不改变 XHS 上游二进制、Cookie 格式、MCP 协议、容器网络或账号登录方式。

## 模块设计与数据流

1. sidecar 启动后每 2 秒检查一次容器内 `127.0.0.1:18060`。
2. 最多检查 450 次，即 15 分钟；通常命中持久化 cache 后会快速就绪。
3. 超时前输出最多 80 行、64 KiB 容器日志，再执行现有 sidecar 回滚。
4. Paramiko sudo 发布 channel 最多等待 1200 秒，覆盖 XHS 15 分钟窗口、主容器健康检查和运维脚本安装，同时仍能在异常时自动终止。

## 测试方案

- 静态测试锁定 450 次就绪检查、失败日志边界和 1200 秒远端总等待。
- 对新镜像启动隔离 XHS sidecar，观察首次浏览器下载、解压和 18060 端口就绪。
- 重新执行完整云端流水线，确认不可变 Digest 部署、双容器状态和公网健康。

## 验收标准

- 无浏览器 cache 时不再在 180 秒被误判失败。
- sidecar 与主容器均使用目标不可变 Digest，状态正常且无重启循环。
- 五个 MCP 完成初始化，携程浏览器依赖存在，公网 `/health` 返回 `status=ok`。
- 部署失败时旧服务可回滚，日志输出不超过既定边界。
