# 工作流完整用户任务模型设计

## 背景

当前工作流已经具备画布、调度、工具查询、智能处理、条件和通知能力，但部分表单直接暴露了 cron、秒数、站码、POI ID、经纬度、变量表达式和原始 JSON。普通用户知道自己想“每天九点运行”“查重庆南岸区天气”“整理上一步结果”，不应理解这些内部协议。可预期的节点错误还可能落成 HTTP 500，使界面只能显示 `REQUEST_FAILED`。

## 目标

- 每个节点都使用用户任务语言，内部协议值由界面或运行时生成。
- 所有可预期失败返回稳定错误码和可操作的中文提示。
- 工具测试先展示摘要，原始响应仅在折叠详情中提供。
- 发布前检查覆盖触发器、处理节点、条件、通知和个人连接，不等到运行后才暴露明显缺项。

## 范围边界

- 保留现有安全节点集合和独立 WorkflowRuntime，不接入 AgentLoop 或聊天 Session。
- 不加入脚本、Shell、循环、子工作流或任意工具调用。
- API 与存储仍可使用 cron、站码、POI ID 和变量引用；普通界面不要求用户手写。
- 外部服务不可用时不伪造成功，返回明确的服务或配置错误。

## 模块设计

### 触发器

用户选择仅手动、每隔一段时间、每天、每周、每月或只执行一次。界面把这些选择编译为现有 `manual`、`interval`、`cron`、`date` 配置；cron 仅作为内部值保存。

### 外部工具

- 天气只接收地点和日期范围；Open-Meteo 无法识别中文详细地址时，自动用高德文本搜索与详情查询补坐标。
- 火车票只接收出发地、目的地和日期；运行时自动查询 12306 站码。
- 地点详情的 POI ID 查询作为内部 helper 隐藏；用户通过地点名称搜索。
- 工具 schema 中的内部或无产品语义参数不直接暴露，明确支持的枚举使用中文选项。

### 智能整理、模板与条件

- 上游输入使用“选择前面步骤”下拉，内部生成 `${nodes.<id>.output}`。
- 智能整理提供摘要、提取重点、改写、分类和自定义任务，生成内部 instruction。
- 内容模板允许编辑普通正文，并通过按钮插入前置结果，界面以中文标签呈现。
- 条件使用结果来源、中文判断方式和比较值，不展示“左值/右值”。

### 通知与邮件

- 官方通知说明实际接收者和通道可用性。
- 个人邮件必须选择当前用户已绑定且有效的发送账号；没有账号时直接给出绑定指引。
- 标题和正文复用前置结果选择器。

### 错误与结果

API 将权限、参数、地点、连接、发布校验和节点执行错误映射为稳定状态码。前端显示失败位置、原因和下一步；工具测试默认展示条数、地点、天气或文本摘要，原始 JSON 放入“查看详细响应”。

## 数据流

```text
用户任务输入 -> 前端编译内部配置 -> 发布前校验 -> WorkflowRuntime
            -> helper 参数适配 -> MCP/LLM/通知节点 -> 摘要与稳定错误
```

## 测试方案

- 单测中文地点降级、站名转站码、helper 隐藏和错误映射。
- 单测全部节点处理器可执行，防止处理器丢失。
- 前端单测工具字段产品化、错误中文化和调度编译。
- 运行后端 workflow 测试、前端 lint/typecheck/test/build。
- 在真实登录页面逐项检查节点表单，并实测“重庆南岸区天气”。

## 验收标准

- 普通界面不要求填写 cron、秒数、经纬度、站码、POI ID、变量表达式或 JSON。
- 所有节点有明确的必填项和发布前提示。
- 可预期失败不再返回无信息的 HTTP 500/`REQUEST_FAILED`。
- 智能整理、模板、条件、官方通知和个人邮件处理器均可被运行时找到。
- 真实页面中的重庆南岸区天气测试成功，并展示简洁摘要。
