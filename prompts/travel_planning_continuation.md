继续完成当前旅行规划。不要汇报中间步骤，也不要因为已经加载 Skill 或完成部分查询而结束。若用户刚选择候选方案，当前 Turn 是新的最终化阶段：即使历史中曾经出现同名 Child 或失败摘要，只要本轮 `delegate_tasks` 可见，就必须先且只调用一次两任务并发批次；`travel-final-stay` 必须处理所选候选全部不同过夜区域的具体住宿身份与各自入住日期价格状态，每个不同过夜城市或区域最多调用一次 dated 酒店查询，不能只查目的地市区酒店后让栾川等第二住宿继续使用估算；`travel-final-route` 必须逐条处理服务端所选候选中的全部本地路线，不少于 2 公里的未定接驳也算，远郊景点的去程和返程都要列入任务，禁止只写“至少覆盖”后漏掉返程。严格沿用服务端注入的所选候选骨架和本 Session 已有证据，只补具体酒店价格、缺失坐标与公共交通线路；不得重新运行完整天气、铁路、网页、社区、景点研究或 optimizer。fan-in 后复用两项结果，一次构造最终计划并调用 finalizer，不得用普通文本宣布无法完成。高德检索必须显式带目的地城市；返回的 province/city/district 不含目标城市时丢弃，禁止把异地同名地点坐标写入计划。

若 `search_travel_hotels` 或 hotel-browser 已出现，必须查询指定日期的酒店账号观察价。酒店 Tool 只读，不执行预订、付款、取消、领券或 App 跳转；认证失效时转为规划预算并记录需要 Owner 重新验证。住宿的 `evidence_ids` 只证明酒店名称、地址与坐标，`price_source_evidence_ids` 只证明指定日期价格；规划估算不得引用景点或普通 POI 作为价格来源。用户没有预算或住宿档位时优先观察结果的中低价舒适型住宿，除非明确要求，不默认选择豪华品牌；成功取得观察价后不得继续使用模型估算。
多日行程且用户未明确免住宿时，最终计划必须至少包含一个具体酒店。最终住宿子任务应先用携程按日期、城市和预算上限取得真实候选，再用返回的准确酒店名到高德核验地址和坐标；不得默认指定全季、汉庭等连锁品牌，也不得给已查到的高价酒店伪造低价估算。hotel-browser 不可用时才用高德“城市 + 候选区域 + 酒店”保留额度补齐名称、地址、坐标和身份来源，再单独标注规划估算。成功天气结果必须在每个 `weather_summary[]` 写入真实 `provider` 和 `freshness`。`TRAVEL_STAY_REQUIRED` 只补住宿与接驳，`TRAVEL_WEATHER_EVIDENCE_MISSING` 只从已有天气结果补来源字段，不得重查整套来源。
距离不少于 2 公里且 mode 包含公交/地铁，或 mode 仍是“规划估算”但承担本地接驳的路线，都必须使用真实高德公交结果及 `transit_legs`；远郊景点要同时覆盖去程与返程，`TRAVEL_ROUTE_EVIDENCE_MISSING` 只补这些路线。已有 12306 去程/返程查询无论返回真实车次还是 `not_on_sale` 都必须分别保留到 `transport_options` 与 evidence；`TRAVEL_RAIL_EVIDENCE_MISSING` 只复用已有票务结果补齐，禁止删除铁路选项或重查。`walking_distance` 单位为米且必须在 0 到 2000 之间；高德候选步行超过 2000 米时应选择更合适的公共交通方案，不得把米误写成公里或超出 schema。去程列车 arrival 必须不晚于首日第一项活动，返程列车 departure 必须不早于末日最后一项活动；冲突时改用已有 12306 结果中的合适车次，禁止篡改时刻。

行程日期在今天起 16 日内时必须优先调用 `get_forecast` 并保留为 live 天气，历史天气只能补充。Tavily 或小红书已有可用结果时，最终 evidence 各保留 1～3 条标题、实际来源链接和筛选摘要，不得声称未查到；`TRAVEL_WEATHER_FORECAST_REQUIRED`、`TRAVEL_WEATHER_FORECAST_EVIDENCE_MISSING`、`TRAVEL_WEB_EVIDENCE_MISSING`、`TRAVEL_SOCIAL_EVIDENCE_MISSING` 都只复用或补对应缺口后重提。

下文“继续逐类调用来源并执行 optimizer”的全量流程只适用于尚未生成候选或尚未请求用户选择的阶段。用户已经选择候选时，本条优先级高于下文全量流程：禁止重新运行 optimizer 或重查天气、铁路、网页、社区和景点，只允许按第一段定向补住宿价格与路线缺口。候选数量采用当前动态规则并覆盖下文旧的“至少两个”表述：短途且真实取舍明显最多三个，中等天数通常两个，时间足够覆盖核心兴趣或差异不足时允许一个；禁止换序凑候选。

`TRAVEL_SOURCE_ALREADY_SATISFIED` 和 `TRAVEL_SOURCE_STABLY_UNAVAILABLE` 都是当前 Session 的来源终态：前者复用成功结果，后者透明降级，均不得改参数或关键词重试。小红书第一次固定为“目的地旅游攻略”；只有返回真实空数组时才允许用一个已取得景点重试一次“景点攻略”，已返回笔记、认证失败、超时或限流均不得重试。

你必须继续逐类调用当前已出现的地图、天气、铁路交通、网页搜索和小红书只读数据源、执行 travel-planner optimizer。高德文本/详情结果已有 `location` 时直接复用，只有缺坐标地点才调用 geocode；geocode 省市与目标城市不一致时丢弃。用路线 Tool 核对相邻活动，并必须覆盖抵达站到酒店/首个活动、末个活动到返程站；高德公交结果必须保留线路号、上下车站和途经站，`walking_distance` 单位为米。模型可以批量提交路线查询，运行时会按高德账号 QPS 串行节流并在瞬时超限时有界重试一次。只要本轮高德公交返回过线路，最终计划至少保留一段 `source=amap_transit` 且含 `transit_legs` 的路线，不得全部降级为规划估算。12306 必须先使用站码 Tool，并把 ToolResult 返回的 `station_code` 原样用于 `get-tickets`，不得猜测站码；工具未激活时先 discover 站码能力，`TRAVEL_STATION_CODE_UNVERIFIED` 时补查站码。两端都有站码才分别查询去程和返程；任一端无站码时铁路明确为不适用，直接收敛为大巴、自驾或包车方案，真实汽车站、班次或攻略价格可作为来源，否则透明标为规划估算，只有用户明确偏好铁路才考虑最近铁路站接驳。`not_on_sale` 是有效核对结果，按其 `sale_open_date` 写入复核项，不要当成无票或接口失败。Tavily 首次返回真实空结果时，把组合词缩短成“城市 + 单景点/主题”重试一次；小红书按上一段“目的地旅游攻略 → 单景点攻略”执行；认证失效不盲目重试。同一轮不要并列调用多个 Tavily 查询，已有成功结果时保留它，不因补充查询超时而把整类来源判为失败。`TRAVEL_SOURCE_ALREADY_QUERIED` 表示当前 Session 已有同参数结果，直接从上下文复用；`TRAVEL_SOURCE_BUDGET_EXHAUSTED` 表示该来源已达到硬上限，必须用已有证据或 unknown 收敛，禁止改写同义参数绕过。按当前动态规则准备一至三个有真实取舍且可行的候选：短途最多三个，中等天数通常两个，天数足够覆盖核心兴趣或差异不足时允许一个；optimizer 的 `days[].route_segments` 只放目的地内的本地接驳，跨日区域变化必须补进入新区的接驳；跨城铁路只进入最终顶层 `transport_plan` 与铁路 evidence，禁止用高德跨城公交冒充高铁或把跨城距离计入日内强度。候选未达到当前天数应有的差异时读取拒绝原因定向调整一次；第二次仍失败必须结束本轮，不继续盲目续跑。通过后把 `feasible_candidates` 原样传给 `request_travel_candidate_review`；若其中存在内部 `itinerary`、`budget_items` 一并传入，运行时未暴露这些字段时摘要仍可提交。用户已选择时严格沿用并复用该候选已取得的 evidence，只补真实缺口，不得重查整套来源；在 `finalize_travel_plan` 传入所选 candidate_id，以成功保存完整计划作为完成终态，不得为了匹配 route_minutes/route_distance_km 凑路线数值。铁路方案写入车次、时间、席别和价格；住宿写入具体酒店、入住退房日期，并严格区分指定日期观察价与规划估算；最终强度分限制在 0 到 10。若 finalizer 返回 `TRAVEL_RESEARCH_INCOMPLETE`，只继续调用尚未尝试或只返回一次空结果的已配置来源；若 finalizer 返回 `TRAVEL_EVIDENCE_INSUFFICIENT`，把成功 ToolResult 归一化为非 model_estimate evidence 后再提交；若 finalizer 返回 `TRAVEL_TRANSIT_EVIDENCE_MISSING`，从已有高德结果补齐线路与站点，不得重查或改成估算。若确实缺少只能由用户决定的必要信息，调用 `request_travel_clarification` 一次列出全部问题。若单个工具或外部来源失败，按既有旅行规则降级、修正或记录 unknowns；不得跳过全部来源，也不得仅用自然语言把内部执行问题交给用户。

候选已经选择后，先确认并行住宿与路线结果已经 fan-in，再调用 finalizer；不要在来源尚不完整时用 finalizer 试探缺口。finalizer 返回结构错误时只修改错误字段并直接重提；每条 evidence 必须始终包含 `evidence_id`、`source_type`、`provider`、`title`、`source_url`、`retrieved_at`、`freshness` 七个必填字段。禁止重新搜索无关来源、重新运行 optimizer 或重写已经通过的交通、天气、住宿与证据部分。服务端已提供 RFC 3339 时间基准时直接使用，禁止再 discover 当前时间或调用诊断 Tool。
